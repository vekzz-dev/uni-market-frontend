## Objetivo

Dejar la ingeniería del frontend lista para ejecutar: qué se construye, con qué decisiones y por qué, cómo se comparte código entre web y móvil, cómo se consume el contrato OpenAPI sin escribir un cliente a mano, y en qué orden se entrega cada capacidad visible.

## Specs

- **S1 — Monorepo único para ambos clientes**: "quiero que sea un monorepo" (L1). Ambas apps y todo el código compartido viven en un solo repositorio con workspaces.
- **S2 — Web en React con JS y CSS puro**: "con react para web ... utiliza js y css puro" (L1). Sin TypeScript, sin frameworks de CSS, sin CSS-in-JS.
- **S3 — Móvil en React Native con Expo, en JS**: "react native con expo para mobile" (L1).
- **S4 — Cliente HTTP generado, prohibido escribirlo a mano**: "Consumen exclusivamente el cliente HTTP generado desde el OpenAPI (prohibidos clientes escritos a mano)" (`uni-market-api/docs/prd.md:101`).
- **S5 — Obligaciones de producto trasladadas al frontend**: "guardas de sesión y rol, refresh transparente ante `401`, validación en espejo al contrato, render seguro sin HTML inyectado, WCAG 2.2 nivel AA (contraste, foco visible, objetivo táctil mínimo, estados no basados solo en color, `prefers-reduced-motion`), temas claro/oscuro e interfaz en español" (`uni-market-api/docs/prd.md:101`).
- **S6 — Contrato de transporte**: base `/v1`; envelope de colecciones `{datos, paginacion}`; cursor opaco en catálogo e historial de mensajes (historial **hacia atrás**: la primera página son los más recientes) y offset con `total`/`totalPaginas` en paneles; errores RFC 9457 `application/problem+json` con `{type,title,status,detail}` y **sin** campo de código de máquina (`uni-market-api/openapi.yaml:1104-1128,1223-1241,1501-1523`).
- **S7 — Sesión**: access token de 15 min en memoria y refresh de 30 días persistido; rotación con detección de reuso: "reuse → **401** + whole family revoked" (`uni-market-api/openapi.yaml:68-92`, `docs/prd.md:81`).
- **S8 — Subidas multipart, sin URLs prefirmadas**: "URLs prefirmadas de subida al storage: la única puerta de subida es la API multipart" (`uni-market-api/docs/prd.md:124`); crear anuncio con 1..5 imágenes de 5 MB (partes repetidas `imagenes`) y avatar de 2 MB (parte `archivo`).
- **S9 — No-objetivos heredados**: "Chat en tiempo real: sin WebSocket/STOMP, sin push y sin eventos de mensaje; el refresco es on-demand o por polling del cliente", "Edición o borrado de mensajes: el historial es inmutable por diseño", "Borrado de conversaciones", "Búsqueda insensible a acentos: `electronica` no encuentra `Electrónica`" (`uni-market-api/docs/prd.md:119,122,123,128`).
- **S10 — Ingeniería primero**: "ayudame a construir primero la ingenieria" (L1) — esta feature entrega diseño y decisiones verificables antes de cualquier pantalla.
- **S11 — Identidad visual adoptada y accesible**: "adaptala y arregla lo que deba ser arreglado" (L3). La identidad entregada (Ember, L2) se adopta con las correcciones que exija la medición de contraste WCAG 2.2 AA del PRD (`docs/prd.md:101`, `:112`), con tema oscuro derivado, y cada corrección queda verificada por pruebas ejecutables.
- **S12 — Diseño visual en OpenPencil, una página por vista, precios en USD**: "Utiliza una pagina por vista, y si van en dolares" (L4), **enmendado** por L6 (agrupar web y móvil) y por L16 (partir el flujo en una página por vista). Cada página contiene **web y móvil juntos con sus estados debajo** (ver `design-system.md` §8), y los precios se formatean en dólares (`$`), decisión D18.

## Decisiones de diseño de esta feature

- **Nivel documental: Standard con sesgo riguroso** y por qué: dos plataformas, datos personales y credenciales de sesión, tres roles con permisos distintos, y un PRD del backend que ya exige WCAG 2.2 AA y cliente generado. Eso no es "prototipo de un archivo": es riesgo repartido entre apps. Se documenta en cuatro documentos con dueño y frecuencia de cambio distintos en vez de un documento monolítico, y se evita duplicar el PRD del backend: se enlaza.
- **El contrato se versiona, no se asume**: el `openapi.yaml` de la API se copia a `openapi/uni-market.yaml` con su referencia de origen registrada, y un script de sincronización (`pnpm contract:sync`) lo actualiza desde ruta local o URL fijada a un tag/SHA. Una comprobación de deriva en CI regenera el cliente y falla si hay diferencias.
- **Código compartido real, no copiado**: `packages/core` (sesión, errores, paginación, validación espejo, capacidad por rol), `packages/api-client` (generado + envoltura fina) y `packages/design-tokens` (una sola fuente de tokens). Las apps no se llaman entre sí.
- **Sin decisiones de marca inventadas**: la paleta final y la tipografía quedan como `Pregunta abierta` (Q-BRAND). El sistema de diseño define roles semánticos y estructura de tokens; los valores quedan marcados `Propuesto` hasta que el usuario decida.
- **Desviación consciente del PRD del backend detectada**: `uni-market-api/docs/prd.md:129` dice "cada app en su repositorio propio". Este monorepo agrupa ambos clientes en un repositorio. La intención que el PRD protege (el repo de la API es exclusivamente backend, sin JS ni tooling frontend) se respeta; la separación web/móvil en dos repos, no. Ver Q-REPO.

## Criterios de aceptación

- Los cuatro documentos existen, se referencian entre sí sin duplicar contenido y toda afirmación sobre la API lleva su `archivo:línea`.
- Toda obligación del PRD trasladada al frontend aparece citada verbatim (S4, S5, S8, S9) y trazada a una decisión o a una tarea concreta (ver Trazabilidad).
- Ninguna afirmación contradice el contrato: `pagina`/`limite` (no `page`/`size`), cursor solo donde el contrato lo define, `422` para reglas de negocio y `400` para estructura.
- Existen explícitas las preguntas abiertas que el usuario debe decidir (Q-REPO, Q-BRAND, Q-DRIFT) y ninguna decisión de marca queda inventada como si fuera firme.
- El plan de slices cubre las 16 reglas de negocio R1–R16 que tocan interfaz y los tres roles.
- Cero contradicciones entre documentos sobre la propiedad del código (qué vive en `api-client` y qué en `core`).
